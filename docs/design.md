# 多应用上线记录系统设计

本文是系统的设计依据。做业务改动前先读本文；需求改变设计时，先更新本文，再改代码。

## 1. 目标

公司有多个应用，上线时间、上线内容和审批过程目前分散在聊天记录里。系统要提供一个统一的上线记录：

1. 每个应用有独立的应用档案。
2. 普通用户提交上线申请，写清上线内容、计划时间和影响范围。
3. 管理员审批，确认上线时记录实际上线时间。
4. 所有人能查到某个应用什么时候上了什么，历史记录不可随意丢失。

## 2. 角色

| 角色     | 主要工作                                         |
| -------- | ------------------------------------------------ |
| 普通用户 | 提交上线申请，查看全部上线记录，维护自己的申请   |
| 管理员   | 审批或驳回申请，确认上线并记录时间，维护应用清单 |

规则：

- 一个账号只属于一个角色。
- 管理员不提交上线申请，因此不存在审批自己申请的情况。
- 普通用户只能操作自己提交的申请，不能审批、确认上线或维护应用。

## 3. 核心对象

### 3.1 应用

| 字段     | 说明                     | 规则                                   |
| -------- | ------------------------ | -------------------------------------- |
| 应用名称 | 如 `订单中心`            | 必填，全系统唯一                       |
| 应用编码 | 如 `order-center`        | 选填；填写时全系统唯一，便于统计和对接 |
| 负责人   | 应用负责人               | 选填                                   |
| 是否启用 | 是否还能提交新的上线申请 | 默认启用                               |
| 备注     |                          | 选填                                   |

规则：

- 应用不物理删除，只能停用。
- 停用后的应用不能在新的上线申请中选择，已有上线记录不受影响。
- 应用名称和编码在保存时校验唯一性。

### 3.2 上线记录

| 字段         | 说明                     | 规则                                         |
| ------------ | ------------------------ | -------------------------------------------- |
| 应用         | 本次上线的应用           | 必填，从已启用的应用中选择                   |
| 版本号       | 如 `v1.2.0`              | 选填                                         |
| 上线内容     | 本次上线做了什么         | 必填，多行文本                               |
| 影响范围     | 受影响的模块、用户或业务 | 选填，多行文本                               |
| 回滚方案     | 出问题时如何回滚         | 选填，多行文本                               |
| 计划上线时间 | 计划什么时候上线         | 必填，精确到分钟                             |
| 实际上线时间 | 实际完成上线的时间       | 管理员确认上线时填写，精确到分钟             |
| 申请人       | 提交申请的人             | 系统自动填写当前用户                         |
| 审批人       | 通过或驳回申请的管理员   | 系统自动记录                                 |
| 审批意见     | 管理员的审批说明         | 驳回时必填，通过时选填                       |
| 状态         | 见第 4 章                | 只能通过流程动作改变                         |
| 附件         | 发布单、截图、脚本等     | 选填，支持多个；只做上传和下载，不做在线预览 |
| 备注         | 其他补充                 | 选填                                         |

时间统一使用 `Asia/Shanghai`，精确到分钟。

## 4. 状态与流程

### 4.1 状态

| 状态   | 含义                                 |
| ------ | ------------------------------------ |
| 待审批 | 申请人已提交，等待管理员处理         |
| 待上线 | 管理员已通过，等待实际上线           |
| 已上线 | 管理员已确认上线，实际上线时间已记录 |
| 已驳回 | 管理员驳回了申请                     |
| 已撤回 | 申请人在待审批阶段撤回了申请         |
| 已取消 | 管理员在审批前或上线前取消了申请     |

### 4.2 流程

```text
提交 ──▶ 待审批 ──通过──▶ 待上线 ──确认上线──▶ 已上线
             │                │
             ├──驳回──▶ 已驳回
             ├──撤回──▶ 已撤回
             └──取消──▶ 已取消
```

规则：

1. **提交。** 普通用户填写上线记录并提交，状态变为待审批，申请人和提交时间由系统记录。
2. **撤回。** 申请人只能撤回自己的待审批申请，撤回后状态为已撤回。
3. **审批通过。** 管理员通过后，状态变为待上线，记录审批人和审批时间；通过时审批意见选填。
4. **驳回。** 管理员驳回时必须填写审批意见，状态变为已驳回。
5. **重新提交。** 已驳回或已撤回的申请，申请人可以修改后重新提交，状态回到待审批；上一次审批人和审批意见清空，但操作历史保留。
6. **确认上线。** 管理员在待上线状态确认上线，填写实际上线时间，默认当前时间；确认后状态变为已上线。
7. **取消。** 管理员可以在待审批或待上线状态取消申请，必须填写取消原因，状态变为已取消。
8. **锁定。** 已上线和已取消的记录不能再修改，也不能删除；需要变更时新建一条上线记录。
9. **内容锁定。** 审批通过后，上线内容、计划时间等申请内容不能再修改。
10. **操作历史。** 每次提交、撤回、通过、驳回、重新提交、确认上线、取消都记录操作人、操作时间和说明，在申请详情中按时间展示。

## 5. 页面

首版保持简单，不单独做“我的申请”和“待我审批”页面，用列表筛选解决。

| 页面         | 谁能打开     | 内容                                                                                                                                                                                           |
| ------------ | ------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 上线记录     | 所有登录用户 | 上线记录列表，显示应用、版本号、上线内容摘要、计划上线时间、实际上线时间、状态、申请人、审批人；支持按应用、状态、时间范围筛选和关键字搜索；提供“只看我的”快捷筛选；普通用户显示“新建申请”按钮 |
| 上线记录详情 | 所有登录用户 | 展示完整字段、附件和操作历史；按角色和状态显示可执行操作                                                                                                                                       |
| 应用管理     | 仅管理员     | 应用列表；新建、编辑、停用应用；不提供删除                                                                                                                                                     |

操作入口：

- 普通用户：在列表或详情中新建、编辑自己的已驳回/已撤回申请，撤回自己的待审批申请。
- 管理员：在列表行内或详情中通过、驳回，在待上线记录中确认上线，在待审批/待上线记录中取消。
- 所有操作完成后刷新列表，状态和操作历史立即反映最新结果。
- AI 对话：所有登录用户可从顶栏机器人按钮打开；应用管理页另有“AI 对话”按钮，方便管理员在维护应用时直接提问或整理内容。

## 6. 权限

| 操作                 | 普通用户                  | 管理员         |
| -------------------- | ------------------------- | -------------- |
| 查看上线记录         | 全部，只读                | 全部           |
| 新建上线申请         | 是                        | 否             |
| 编辑申请             | 仅自己的已驳回/已撤回申请 | 否             |
| 撤回申请             | 仅自己的待审批申请        | 否             |
| 通过、驳回           | 否                        | 是             |
| 确认上线             | 否                        | 是             |
| 取消申请             | 否                        | 是，需填写原因 |
| 新建、编辑、停用应用 | 否                        | 是             |
| 删除上线记录或应用   | 否                        | 否             |

所有限制都在服务端生效：列表和详情按权限返回数据，直接调用越权接口返回 403 或 404。页面隐藏按钮只是为了使用方便，不能替代服务端校验。

## 7. AI 助手

AI 助手用于提问和内容整理，不参与上线申请的提交、审批或状态变更。

### 7.1 入口与使用人群

| 入口           | 谁能使用     | 说明                                                 |
| -------------- | ------------ | ---------------------------------------------------- |
| 顶栏“AI 对话”  | 所有登录用户 | 在任意业务页面打开右侧对话面板                       |
| 应用管理页按钮 | 仅管理员     | 在维护应用清单时直接打开对话面板，用于提问或整理内容 |

### 7.2 模型

- 对话模型在“Agent 管理 › 模型服务”中配置和启用，业务页面不重复维护模型清单。
- 新会话可以选择模型；已有会话可以切换模型，但上下文仍属于当前会话。
- 模型服务的 API Key 只填写在模型服务的专用密钥字段，不写入设计文档、需求或源码。

### 7.3 会话与隔离

- 会话和消息存储在服务端，刷新页面或重新登录后仍可继续历史会话。
- 会话列表只返回当前用户自己的记录。
- 读取会话详情、历史消息、发送消息和停止生成都校验会话归属；直接访问他人的会话返回 403 或 404。
- 不提供会话分享入口，也不创建分享记录。

### 7.4 工具与业务数据

- 本版本不注册任何业务工具，AI 不读取或修改上线记录、应用清单等业务数据。
- 原生会话的工具列表置空，不启用 bash、skill、网页搜索等能力。
- 若后续需要接入业务记录，必须注册最小工具集，并在工具执行时校验当前用户的数据权限。

### 7.5 验收标准

- 顶栏和应用管理页都能打开对话面板。
- 模型选择器列出已启用的对话模型，选择后能收到真实回复。
- 生成过程中可以停止，停止后已生成的内容仍保留在会话中。
- 刷新页面后能从历史列表重新打开会话，并继续追问。
- 两个账号互相看不到对方的会话；直接请求他人的会话被拒绝。
- 对话不会改动任何业务数据。

## 8. 设计规范

沿用 NocoBase 3 内置设计规范：shadcn/ui 组件、模板主题变量、标准列表、表单和抽屉。不单独修改颜色和字体。用户可见文案走应用的 i18n 机制，首版以中文为主，同时保留英文文案。

## 9. 范围

### 9.1 本版本包含

- 应用清单的维护和停用
- 上线申请的新建、编辑、撤回和重新提交
- 管理员审批、驳回、确认上线、取消
- 实际上线时间记录
- 附件上传和下载
- 列表筛选、搜索和“只看我的”
- 普通用户和管理员两个角色的权限控制
- 顶栏和应用管理页的 AI 对话入口
- 模型选择、停止生成、历史会话和按账号隔离

### 9.2 本版本不做

- 站内信、邮件或其他通知
- 评论和讨论
- 多级审批
- 自动部署、自动回滚或回滚执行
- 附件在线预览
- 导入、导出
- 移动端专门适配
- 上线日历、甘特图或统计报表
- 应用删除
- AI 读取或修改业务数据
- 会话分享
- AI 自动提交审批或变更申请状态

## 10. 分步交付计划与验收

### 第 1 步：应用清单

**交付**

- 应用数据表和校验规则
- 应用管理页面
- 应用列表接口

**验收标准**

- 管理员能新建、编辑、停用应用。
- 应用名称为空或重复时不能保存，并在对应输入框旁提示。
- 应用编码填写重复时不能保存。
- 停用后的应用不出现在新建上线申请的应用选择中。
- 已有上线记录的应用停用后，历史记录仍能正常查看。
- 刷新页面后应用数据仍在。

### 第 2 步：上线申请与审批

**交付**

- 上线记录数据表和状态规则
- 上线记录列表、详情和新建/编辑页面
- 提交、撤回、通过、驳回、重新提交接口
- 申请人只能操作自己申请的权限控制

**验收标准**

- 普通用户能新建申请，提交后状态为待审批，申请人为当前用户。
- 普通用户能看到全部上线记录，但只能编辑或撤回自己的申请。
- 管理员能看到待审批申请并通过或驳回。
- 驳回时不填审批意见不能提交。
- 已驳回或已撤回的申请能修改后重新提交，状态回到待审批，操作历史保留。
- 审批通过后申请内容不能再修改。
- 列表能按应用、状态、时间范围和关键字筛选，“只看我的”结果正确。
- 普通用户直接调用审批或驳回接口被拒绝。

### 第 3 步：确认上线、取消与权限收口

**交付**

- 确认上线和取消操作
- 实际上线时间记录
- 完整的角色权限和操作历史
- 全流程验收测试

**验收标准**

- 管理员能对已通过的申请确认上线，实际上线时间默认当前时间且可调整。
- 确认后状态变为已上线，实际上线时间正确显示。
- 管理员能取消待审批或待上线的申请，取消原因必填。
- 已上线、已取消的记录不能修改或删除。
- 普通用户直接调用确认上线、取消、应用管理接口返回 403 或 404。
- 管理员没有新建上线申请入口，直接调用新建接口也被拒绝。
- 每个状态动作都在详情中生成一条操作历史，包含操作人、时间和说明。
- 按第 6 章权限矩阵逐项验证，界面显示和接口结果一致。

### 第 4 步：AI 对话入口

**交付**

- 顶栏对话入口和应用管理页的“AI 对话”按钮
- 模型服务复用“Agent 管理 › 模型服务”
- 对话面板的模型选择、停止生成和历史会话
- 按账号隔离的会话服务端校验

**验收标准**

- 所有登录用户能从顶栏打开对话面板，管理员还能从应用管理页打开。
- 模型选择器能列出已启用的对话模型。
- 发送问题后收到真实模型回复。
- 生成过程中点击停止，生成中止且已生成内容保留。
- 刷新页面后能从历史列表重新打开会话并继续追问。
- 另一个账号看不到当前账号的会话，直接访问详情返回 403 或 404。
- 对话过程中没有调用业务工具，业务数据保持不变。
